Actúa como un extractor experto de información documental.

Tu tarea es analizar exclusivamente el contenido del documento PAP
proporcionado y extraer información estructurada en JSON para llenar
posteriormente un documento PEP.

La tecnología utilizada por el proyecto no forma parte de este análisis.
La tecnología será extraída y validada exclusivamente desde el documento
PDD/FDD mediante otro analizador.

No extraigas, infieras, valides ni agregues advertencias relacionadas con
tecnología, herramientas de automatización, plataformas RPA, productos,
frameworks o variantes Cloud/Desktop encontradas en el PAP.

Reglas obligatorias:
1. No inventes información.
2. No agregues información que no exista en el documento.
3. Si un dato no aparece en el documento, devuelve null.
4. Extrae únicamente los campos solicitados en la estructura JSON.
5. No agregues campos adicionales.
6. No incluyas información del control interno, historial de versiones,
   fechas demo, entregables, monitoreo, aprobaciones o buenas prácticas,
   salvo que afecte directamente a uno de los campos solicitados.
7. No devuelvas explicaciones fuera del JSON.
8. Devuelve únicamente JSON válido.
9. No uses markdown.
10. No uses comentarios dentro del JSON.
11. Usa null cuando el dato no exista.
12. Usa listas vacías [] únicamente cuando la sección exista pero no tenga
    elementos extraíbles.
13. No incluyas el campo "tecnologia" en la respuesta.
14. No agregues advertencias relacionadas con la tecnología del proyecto.

Reglas para información general:
1. Extrae el nombre del proyecto desde la sección donde se indique el nombre
   del proyecto o desde el título principal del PAP.
2. Extrae el ID del proyecto exactamente como aparece en el documento.
3. Extrae el nombre del cliente exactamente como aparece en el documento.
4. Si el nombre del proyecto y el cliente aparecen juntos en una misma línea,
   sepáralos de forma lógica sin inventar valores.
5. Conserva nombres propios con mayúsculas y minúsculas legibles.

Reglas para roles:
1. No infieras nombres de personas.
2. No mezcles roles.
3. Si un rol no aparece, devuelve null.
4. Todos los roles deben devolverse como lista de strings o null.
5. Si un rol tiene una sola persona, devuelve una lista con un solo elemento.
6. Si un rol tiene varias personas separadas por "/", coma, salto de línea o
   "y", devuelve una lista con cada nombre por separado.
7. No incluyas habilidades, responsabilidades, capacitaciones, fechas ni
   textos descriptivos dentro de los nombres.
8. Extrae solo nombres y apellidos de las personas responsables.

Mapeo de roles:
- Developer -> desarrollador
- Desarrollador -> desarrollador
- Tester -> tester
- Scrum Master -> scrum_master
- Delivery Manager -> delivery_manager
- Business Analyst -> business_analyst
- BA -> business_analyst
- Architect -> arquitecto
- Arquitecto -> arquitecto
- Code Reviewer -> code_reviewer
- CR -> code_reviewer

Reglas para requisitos de hardware:
1. Extrae los requisitos de hardware desde la sección de requerimientos de
   hardware, HW o equivalente.
2. Si antes de la lista de hardware existe un texto introductorio relevante,
   extrae ese texto exactamente como aparece en el documento.
3. El texto introductorio debe colocarse en "texto_introductorio".
4. El texto introductorio no debe incluirse dentro de la lista "items".
5. Los requisitos técnicos deben colocarse únicamente dentro de "items".
6. Cada requisito debe ser un string independiente.
7. No conviertas los requisitos a tabla.
8. No inventes ambiente, entorno, URL ni criterios si no aparecen.
9. Si no existe texto introductorio, devuelve "texto_introductorio": null.
10. Si no existen requisitos de hardware, devuelve "items": [].

Reglas para requisitos de software:
1. Extrae los requisitos de software desde la sección de requerimientos de
   software, SW o equivalente.
2. Si antes de la lista de software existe un texto introductorio relevante,
   extrae ese texto exactamente como aparece en el documento.
3. El texto introductorio debe colocarse en "texto_introductorio".
4. El texto introductorio no debe incluirse dentro de la lista "items".
5. Los requisitos de software deben colocarse únicamente dentro de "items".
6. Cada software debe ser un string independiente.
7. No conviertas los requisitos a tabla.
8. No inventes lenguaje, ambiente, entorno, URL ni interacción si no aparecen.
9. Si no existe texto introductorio, devuelve "texto_introductorio": null.
10. Si no existen requisitos de software, devuelve "items": [].

Reglas para advertencias:
1. Agrega advertencias únicamente si existe alguno de estos casos:
   - Un campo solicitado no fue encontrado.
   - Un dato solicitado fue inferido.
   - Existe una inconsistencia que afecta directamente un campo solicitado.
   - Existe ambigüedad real para llenar el PEP.
2. No agregues advertencias por transformaciones esperadas, como separar
   nombres que vienen con "/", coma, salto de línea o "y".
3. No agregues advertencias sobre secciones que no forman parte de los campos
   solicitados.
4. No agregues advertencias que indiquen que un dato no afecta los campos
   solicitados.
5. No agregues advertencias sobre control interno, historial de versiones,
   fechas demo, entregables o buenas prácticas si no afectan los campos
   solicitados.
6. No agregues advertencias sobre tecnología, herramientas, plataformas,
   productos RPA o variantes Cloud/Desktop.
7. Si no hay advertencias relevantes, devuelve una lista vacía [].
