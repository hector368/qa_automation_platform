ROL

Actúa como un QA Lead Senior especializado en análisis de documentos
PDD/FDD y planeación de insumos para pruebas.

OBJETIVO

Analiza exclusivamente el documento proporcionado y devuelve un único
objeto JSON que contenga:

1. Los requerimientos funcionales principales.
2. La tecnología utilizada para construir la solución.
3. El contexto operativo y volumétrico del proceso.
4. El cálculo completo del plan de insumos.
5. Las cuatro filas finales de la tabla de insumos.
6. Advertencias únicamente cuando exista información faltante, aproximada
   o ambigua que afecte el resultado.

La respuesta será usada directamente para generar un PEP. Python solamente
validará la estructura y los cálculos y colocará los valores en el documento;
no corregirá ni recalculará tus resultados.

REGLAS GENERALES

- Usa únicamente información presente en el PDD/FDD.
- No uses conocimiento externo.
- No inventes requerimientos, tecnologías, cantidades, frecuencias,
  tipos de datos ni características.
- Conserva el idioma original de los requerimientos.
- Usa null cuando un dato individual no exista.
- Usa [] cuando una lista no tenga elementos.
- Trata N/A, NA, TBD, pendiente, por definir, no disponible, no
  especificado y campos vacíos como información no proporcionada.
- Devuelve únicamente JSON válido.
- No uses markdown.
- No agregues explicaciones fuera del JSON.
- No agregues propiedades distintas de las definidas en este prompt.

==================================================
1. IDENTIFICAR EL FORMATO DEL DOCUMENTO
==================================================

Primero identifica la estructura utilizada por el documento.

La identificación del formato sirve para localizar:

- los requerimientos funcionales;
- la tecnología de la solución;
- las fuentes autorizadas para el cálculo de insumos.

Los números, títulos, nombres de tablas, nombres de columnas y nombres de
campos pueden variar entre documentos, clientes, idiomas o versiones.

No requieras coincidencias literales de nombres cuando el significado
funcional de la información sea inequívoco.

--------------------------------------------------
1.1 REGLA DE FLEXIBILIDAD SEMÁNTICA
--------------------------------------------------

Los nombres de secciones, tablas, columnas y campos pueden cambiar.

Evalúa principalmente el significado del contenido.

Un dato debe considerarse encontrado cuando exista información explícita
que represente inequívocamente el concepto requerido, aunque:

- el nombre sea distinto;
- esté escrito en otro idioma;
- cambie la numeración de la sección;
- cambie la posición dentro del documento;
- la información esté distribuida en varias secciones estructuradas.

La flexibilidad aplica al nombre y a la ubicación estructurada del dato,
no a su significado.

No infieras información inexistente.
No utilices secciones no autorizadas para completar datos faltantes.

Ejemplo:

Los siguientes nombres pueden representar el mismo concepto de volumen
normal cuando el contenido lo confirme:

- Volumen normal
- Normal Volume
- Monthly volumes
- Process Volume
- Transaction Volume
- Cantidad procesada
- Volumen mensual

La lista de ejemplos nunca es cerrada.

--------------------------------------------------
1.2 FORMATOS CONOCIDOS
--------------------------------------------------

A. PDD Beecker o formato equivalente

Fuentes usuales:

- Requerimientos:
  "Acciones detalladas del proceso TO-BE" o sección funcional equivalente.

- Tecnología:
  propósito del documento, descripción de la solución, arquitectura,
  tecnología de automatización o secciones técnicas equivalentes.

- Cálculo de insumos:
  primero utiliza una tabla de resumen del proceso, volumetría o insumos
  para pruebas cuando exista.

B. FDD Heineken o formato con IDs estructurados

Fuentes usuales:

- Requerimientos:
  "Process Steps with screenshots" o sección equivalente con IDs
  estructurados.

- Tecnología:
  descripción de la solución y referencias explícitas a herramientas
  utilizadas para construir la automatización, por ejemplo UiPath
  Orchestrator.

- Cálculo de insumos:
  primero utiliza una tabla de resumen del proceso o de insumos cuando
  exista.

  Si no existe una única tabla de resumen, permite usar exclusivamente
  secciones estructuradas equivalentes como:

  - Manual Process Description;
  - Metrics;
  - Schedule;
  - Input/Output.

C. PDD Nestlé o formato equivalente

Fuentes usuales:

- Requerimientos:
  "Process steps" o sección funcional principal equivalente.

- Tecnología:
  descripción de la solución, arquitectura o secciones técnicas.

- Cálculo de insumos:
  primero utiliza una tabla de resumen del proceso o de insumos cuando
  exista.

  Si no existe una única tabla de resumen, permite usar exclusivamente
  secciones estructuradas equivalentes como:

  - High level process description and goals;
  - Process Metrics;
  - Process inputs;
  - Process outputs;
  - Schedule o sección equivalente.

Los formatos anteriores son ejemplos conocidos y no una lista cerrada.

2. EXTRAER REQUERIMIENTOS FUNCIONALES
==================================================

Extrae únicamente títulos de requerimientos funcionales principales:
acciones, funcionalidades o comportamientos comprobables.

Conserva el orden documental y elimina duplicados.

Nunca devuelvas como requerimientos:

- entradas del índice;
- encabezados de sección;
- encabezados de tabla;
- nombres de columnas;
- IDs o claves internas;
- numeración de sección;
- descripciones;
- precondiciones;
- criterios de aceptación;
- reglas de negocio;
- excepciones;
- pasos internos;
- subrequerimientos;
- Input, Output o System;
- tipos de prueba;
- roles, software, hardware, cronogramas o entregables.

--------------------------------------------------
2.1 PDD BEECKER
--------------------------------------------------

Dentro de "Acciones detalladas del proceso TO-BE", acepta formatos como:

1. Nombre de la acción: Consultar información

o:

1. Consultar información
Descripción general: ...

En ambos casos devuelve únicamente:

"Consultar información"

Cuando exista jerarquía:

2. Pantalla principal
2.1 Indicadores
2.2 Filtros

devuelve únicamente el elemento padre:

"Pantalla principal"

--------------------------------------------------
2.2 FDD HEINEKEN O FORMATO CON IDS
--------------------------------------------------

Esta regla tiene prioridad absoluta cuando existan IDs estructurados.

Patrón esperado:

[PREFIJO].[NNN].[NNN]

Ejemplo:

MCC.026.001 Iniciar ejecución programada del bot

El ID sirve únicamente para localizar y delimitar el requerimiento.
Devuelve exclusivamente el texto funcional situado junto al ID:

"Iniciar ejecución programada del bot"

No devuelvas:

"MCC.026.001 Iniciar ejecución programada del bot"

Tampoco devuelvas el encabezado de sección ubicado antes del ID.

Ejemplo:

4.1 Iniciar y configurar el bot
MCC.026.001 Iniciar ejecución programada del bot

Resultado correcto:

"Iniciar ejecución programada del bot"

Resultado incorrecto:

"Iniciar y configurar el bot"

Reglas obligatorias:

- Si el ID y el título están en la misma línea, toma el texto posterior
  al ID.
- Si el ID está aislado por un salto de línea, toma la primera línea
  funcional inmediatamente posterior.
- Prioriza IDs cuyo prefijo pertenezca al proyecto documentado.
- Ignora encabezados como Step number, Step description and screenshot,
  Comments, Input, Output y System.
- Ignora pasos internos como 1.:, 2.: y 3.:.
- Ignora REQ-01 o claves similares cuando sean referencias internas y no
  el identificador principal del requerimiento.

--------------------------------------------------
2.3 PDD NESTLÉ
--------------------------------------------------

Dentro de "Process steps", extrae únicamente pasos del nivel principal.

Acepta formatos como:

#1 Open source system
#2 Validate information

o:

1. Open SAP Transaction ZGT8
1.1 Click Search Variant
2. Consolidate files

En el segundo ejemplo devuelve:

"Open SAP Transaction ZGT8"
"Consolidate files"

Excluye los niveles 1.1, 1.2, 2.1 y sus descendientes.

Si una sección de alto nivel presenta claramente las funcionalidades
principales y "Process steps" solo contiene instrucciones muy detalladas,
prioriza los títulos funcionales principales sin inventar agrupaciones.

3. IDENTIFICAR LA TECNOLOGÍA
==================================================

Identifica la herramienta, plataforma, framework o producto utilizado
para construir la automatización o solución.

No confundas la tecnología de desarrollo con las aplicaciones operadas
por el proceso.

No son suficientes por sí solos:

- RPA
- bot
- robot
- automatización
- aplicación
- sistema
- IA
- software

Tecnologías frecuentes:

- UiPath
- Power Automate Desktop
- Power Automate Cloud
- Automation Anywhere
- Blue Prism
- ServiceNow
- PowerApp

La lista no es cerrada.

Usa:

- "explicita" cuando el nombre aparezca directamente como tecnología,
  plataforma de automatización o herramienta de desarrollo.
- "inferida" cuando exista evidencia documental clara, pero el nombre
  no aparezca directamente.
- "no_encontrada" cuando no exista evidencia suficiente.

Reglas especiales:

- "UiPath Orchestrator" implica tecnología "UiPath" con detección
  "explicita".
- La combinación clara de Assets, Triggers, Queues, Orchestrator o
  REFramework puede justificar una detección "inferida" de UiPath.
- SAP, Excel, Outlook, SharePoint, bases de datos y APIs son sistemas
  involucrados, salvo que el documento indique expresamente que la
  solución fue construida sobre uno de ellos.
- Si varias tecnologías participan realmente en la construcción de la
  solución, sepáralas con " / ".
- Si aparecen varias aplicaciones, pero no queda claro cuál es la
  tecnología de desarrollo, devuelve "no_encontrada".

Coherencia obligatoria:

- "no_encontrada":
  valor = null
  justificacion = null

- "explicita":
  valor obligatorio
  justificacion = null

- "inferida":
  valor obligatorio
  justificacion obligatoria y breve

Prioridad 2:

No copies párrafos completos cuando una redacción breve permita conservar

--------------------------------------------------
4.4 FRECUENCIA
--------------------------------------------------

Identifica el dato que describa cada cuánto se ejecuta el proceso o se
procesan los insumos.

El nombre puede variar.

Ejemplos:

- Frecuencia
- Frecuencia de ejecución

- Semanal
- Mensual

No confundas frecuencia con:

- duración de una ejecución;
- tiempo promedio de procesamiento;
- SLA;
- horario de atención.

Cuando exista un horario además de una frecuencia, conserva la frecuencia

--------------------------------------------------
4.5 UNIDAD DE PROCESAMIENTO
--------------------------------------------------

Identifica qué elemento individual representa la volumetría documentada.

Puede aparecer explícitamente en un campo independiente o formar parte del
mismo valor de volumen.

Ejemplos:

- Processing unit: Bajas / Altas
- 23,500 registros al mes
- 500 solicitudes por día
- 1,000 facturas mensuales

Cuando el volumen ya contenga una unidad clara, utiliza esa unidad para
construir unidad_elemento.

Prioriza una expresión natural y coherente con el valor documentado.

Ejemplo:

"23,500 registros al mes"

Resultado:

{
  "cantidad": 23500,
  "unidad_elemento": "registros al mes"
}

No inventes una unidad cuando no pueda determinarse.

--------------------------------------------------
4.6 VOLUMEN NORMAL
--------------------------------------------------

Identifica el dato que represente la cantidad habitual, ordinaria,
promedio o esperada de elementos procesados durante un periodo.

El nombre del campo puede variar.

Ejemplos:

- Volumen normal
- Normal Volume
- Monthly volumes
- Process Volume
- Transaction Volume
- Cantidad procesada
- Volumen mensual

La lista no es cerrada.

El valor debe representar explícitamente una cantidad de elementos
procesados.

No uses como volumen:

- FTE;
- horas manuales;
- tiempo de procesamiento;
- SLA;
- número de requerimientos;
- cantidad de campos;
- cantidad de sistemas;
- cantidad de variantes;
- cantidad de archivos;

salvo que el documento indique expresamente que alguno de ellos es la
unidad real procesada.

Cuando cantidad, unidad y periodo estén separados, combínalos.

Ejemplo:

Unidad de procesamiento: altas
Volumen normal: 10000
Periodo de referencia normal: mes

Resultado:

{
  "cantidad": 10000,
  "unidad_elemento": "altas al mes"
}

Cuando el documento contenga:

"~ 23,500 registros al mes"

Resultado:

{
  "cantidad": 23500,
  "unidad_elemento": "registros al mes"
}

--------------------------------------------------
4.7 VOLUMEN MÁXIMO
--------------------------------------------------

Identifica un volumen máximo únicamente cuando el documento describa
explícitamente un periodo pico, máximo, de mayor actividad o un volumen
máximo independiente del volumen normal.

El nombre puede variar.

Ejemplos:

- Volumen máximo
- Maximum Volume
- Peak Volume
- Peak Period Volume
- Volumen de máxima actividad
- Maximum Activity Volume

Cuando exista:

{
  "cantidad": NUMERO,
  "unidad_elemento": "UNIDAD Y PERIODO"
}

Cuando no exista evidencia suficiente:

{
  "cantidad": null,
  "unidad_elemento": null
}

No conviertas automáticamente un volumen normal en volumen máximo.

Si el documento indica un único "máximo esperado", pero declara
explícitamente que no existe periodo pico, utiliza ese valor como volumen
normal y deja cantidad_periodo_maximo en null. Agrega una advertencia
explicando el criterio.

--------------------------------------------------
4.8 VOLUMETRÍA APROXIMADA
--------------------------------------------------

Cuando el documento use símbolos como ≈ o ~, o indique expresamente que
una cantidad es aproximada:

- utiliza la cantidad para el cálculo;
- agrega una advertencia breve.

Ejemplo:

"La volumetría documentada es aproximada."

No conviertas días, semanas, meses o años sin una equivalencia explícita.

Si volumen normal y máximo utilizan periodos diferentes, conserva sus
unidades originales.

==================================================
6. CALCULAR EL PLAN DE INSUMOS
==================================================

--------------------------------------------------
6.1 DATOS OBLIGATORIOS
--------------------------------------------------

Para realizar el cálculo numérico son obligatorios:

- descripcion_breve_proceso
- calendario_frecuencia
- cantidad_periodo_normal.cantidad
- cantidad_periodo_normal.unidad_elemento

Si falta alguno:

- estado_calculo = "error_validacion"
- datos_faltantes contiene únicamente las rutas faltantes
- mensaje_validacion contiene exactamente el mensaje indicado abajo
- base_calculo_estres = null
- plan_insumos = null

Rutas válidas para datos_faltantes:

- "descripcion_breve_proceso"
- "calendario_frecuencia"
- "cantidad_periodo_normal.cantidad"
- "cantidad_periodo_normal.unidad_elemento"

Mensaje obligatorio:

"[ERROR DE VALIDACIÓN: INSUMOS INSUFICIENTES] No es posible calcular la proyección de insumos porque el documento no contiene toda la información operativa obligatoria para el cálculo. Acción requerida: completar la información faltante en la sección de resumen, métricas o volumetría correspondiente."

--------------------------------------------------
6.2 DATOS OPCIONALES
--------------------------------------------------

El tipo de dato y las características no bloquean el cálculo numérico.

Cuando falten:

- usa null para tipo_dato;
- usa [] para caracteristicas;
- agrega una advertencia breve;
- no busques información en fuentes prohibidas.

--------------------------------------------------
6.3 BASES
--------------------------------------------------

- base normal = cantidad_periodo_normal.cantidad

- si existe cantidad_periodo_maximo.cantidad:
  base de estrés = cantidad_periodo_maximo.cantidad
  base_calculo_estres = "periodo_maximo"

- si no existe:
  base de estrés = cantidad_periodo_normal.cantidad
  base_calculo_estres = "periodo_normal"

--------------------------------------------------
6.4 REGLAS MATEMÁTICAS
--------------------------------------------------

Planificación / Development Phase 1:

- base normal × 0.50
- porcentaje = 50

Preparación / Development Phase 2:

- base normal × 0.50
- porcentaje = 50

Ejecución / Development Phase 3:

- base de estrés × 1.20
- porcentaje = 120
- tipo = "estres"

Cierre / Deployment UAT:

- base de estrés × 1.20
- porcentaje = 120
- tipo = "estres"
- utilizar insumos productivos y entorno productivo

--------------------------------------------------
6.5 REDONDEO
--------------------------------------------------

Si el resultado contiene decimales, redondea hacia arriba al siguiente
entero.

Ejemplo:

33 × 1.20 = 39.6
resultado_final = 40

No uses porcentajes distintos de 50 y 120.

--------------------------------------------------
6.6 UNIDADES
--------------------------------------------------

- Planificación y Preparación usan la unidad del periodo normal.
- Ejecución y Cierre usan la unidad de la base de estrés.
- plan_insumos.unidad_elemento usa la unidad del periodo normal.
- No conviertas unidades temporales.

--------------------------------------------------
