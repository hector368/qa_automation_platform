1) FUENTE DE INFORMACIÓN Y NO INVENTAR
=================================================

InputText es el Test Basis principal.

Derivar condiciones de prueba únicamente desde información
explícitamente disponible en:

- Descripción general.
- Precondiciones.
- Pasos de ejecución.
- Criterios de aceptación.
- Reglas de negocio.
- Restricciones funcionales.
- Excepciones.
- Sistema.
- Input.
- Output.
- Actor.

Reglas obligatorias:

- No inventar pasos, campos, datos, reglas, rutas, mensajes,
  reintentos, destinatarios, archivos, sistemas, validaciones,
  excepciones ni comportamientos.
- Si un valor es parametrizable y no existe valor exacto, utilizar
  "según configuración".
- Si existe un mensaje exacto, conservarlo literalmente.
- Si una condición no tiene comportamiento verificable definido,
  no generar un TC independiente para ella.
- Si una RN o EXC no tiene comportamiento esperado definido, no
  inventarlo.
- No completar huecos funcionales mediante conocimiento general.

Aplicar técnicas de diseño de pruebas únicamente cuando InputText
contenga información suficiente:

- Partición de equivalencia y valores límite:
  cuando existan rangos, límites, formatos o valores permitidos.

- Tablas de decisión:
  cuando existan combinaciones explícitas de condiciones.

- Transición de estados:
  cuando existan estados y cambios definidos.

- Casos de uso:
  cuando exista un flujo funcional definido.

=================================================
2) INTERPRETACIÓN DEL FORMATO BA/PDD
=================================================

Cuando InputText contenga apartados estructurados, interpretarlos así:

A) Descripción general

- Utilizarla como contexto funcional.
- Usarla para construir objective, expected_result y alcance del
  Happy Path.
- No convertir automáticamente cada oración en un TC.
- Si describe un flujo completo, utilizarla para construir una
  cobertura funcional integral.

B) Precondiciones

- Mapearlas principalmente a preconditions.
- No convertirlas en steps.
- No crear una Excepción por incumplimiento de una precondición
  salvo que InputText defina explícitamente la consecuencia.
- Cada precondición independiente debe ser un elemento distinto
  de la lista preconditions.

C) Pasos de ejecución PP

- Utilizarlos como fuente principal de steps.
- Los PP representan hitos o subflujos; NO son TCs automáticos.
- Integrar cronológicamente los PP que pertenezcan al mismo flujo.
- Dividir únicamente cuando sea necesario por el límite de steps,
  utilizando hitos funcionales verificables.

D) Criterios de Aceptación

- Utilizarlos principalmente como oráculo para expected.
- Su cumplimiento exitoso debe validarse dentro del Happy Path.
- No crear un TC adicional para cada criterio cuando no cambie
  el outcome del flujo.

E) Restricciones

- Considerar únicamente restricciones funcionales.
- Si producen rechazo, bloqueo, omisión, detención u otra consecuencia
  explícita, pueden generar un TC exception.
- Si únicamente delimitan alcance, incorporarlas al TC correspondiente.
- Ignorar restricciones puramente no funcionales de rendimiento,
  volumen, capacidad o tiempo cuando no exista consecuencia funcional.

F) Reglas de negocio RN

- Tratarlas como condiciones de prueba trazables.
- No crear automáticamente un TC por cada RN.
- Agrupar RN pertenecientes al mismo flujo y outcome.
- Crear TC independiente cuando una RN produzca un outcome diferente:
  error, advertencia, rechazo, omisión, notificación, detención o
  continuación distinta.
- Incluir el identificador RN dentro de action o expected cuando
  aporte trazabilidad.

G) Excepciones EXC

- Evaluar cada EXC explícita.
- Generar TC exception cuando tenga causa y comportamiento esperado.
- Cubrir trigger, respuesta y resultado final.
- EXC con el mismo comportamiento final pueden agruparse cuando no
  se pierda claridad.
- Conservar exactamente mensajes, destinatarios, reintentos,
  detenciones u otras acciones cuando estén definidos.

H) Sistema, Input, Output y Actor

- Sistema:
  utilizarlo para preconditions y contexto operativo.

- Input:
  utilizarlo para preconditions y acciones de lectura, carga,
  descarga o procesamiento.

- Output:
  utilizarlo principalmente para expected_result.

- Actor:
  utilizarlo en preconditions o contexto cuando corresponda.
  No inventar acciones humanas.

=================================================
3) GENERACIÓN Y CLASIFICACIÓN DE CASOS
=================================================

Cada TC debe utilizar exactamente una clasificación:

- "happy_path"
- "exception"

-------------------------------------------------
3.1) HAPPY PATH
-------------------------------------------------

Corresponde al flujo funcional exitoso.

Debe cubrir:

- Inputs válidos.
- Condiciones correctas.
- Reglas exitosas.
- Criterios de aceptación.
- Procesamiento esperado.
- Output final.

Reglas:

- No incluir errores, rechazos, advertencias ni datos inválidos.
- Las validaciones correctas de campos, formatos y condiciones deben
  integrarse dentro del Happy Path.
- No crear micro-TCs para validar individualmente cada condición
  exitosa.
- Los PP pertenecientes al mismo camino exitoso deben conservar su
  secuencia funcional.

-------------------------------------------------
3.2) EXCEPTION
-------------------------------------------------

Utilizar cuando exista una desviación funcional explícita:

- Violación de reglas de negocio.
- Datos inválidos.
- Campos requeridos faltantes.
- Duplicados.
- Datos fuera de rango.
- Restricciones funcionales.
- Excepciones operativas explícitas.
- Rechazos.
- Advertencias.
- Detenciones.
- Notificaciones.
- Flujos alternos.

Generar un TC exception únicamente cuando exista un trigger que
produzca un comportamiento funcional verificable.

=================================================
3.3) COBERTURA POR OUTCOME + TRIGGER
=================================================

Definiciones:

Outcome:
resultado final funcional verificable del TC.

Trigger:
condición que provoca una ruta o comportamiento diferente.

Antes de generar los TCs:

1. Identificar las condiciones funcionales.
2. Identificar sus outcomes.
3. Agrupar condiciones con el mismo comportamiento.
4. Separar aquellas que producen resultados funcionales distintos.
5. Generar únicamente los TCs necesarios para obtener cobertura útil.

Reglas:

- Generar el Happy Path principal.
- Generar exceptions únicamente con soporte explícito en InputText.
- No duplicar TCs con el mismo objective y expected_result.
- No crear TCs individuales por cada campo o variante cuando
  pertenezcan al mismo flujo y outcome.
- Consolidar RN, EXC o variantes relacionadas cuando produzcan
  la misma consecuencia funcional.
- No crear micro-TCs.
- No omitir cobertura únicamente para reducir la cantidad de casos.

Regla importante:

NO agrupar escenarios únicamente porque:

- usen el mismo archivo,
- consuman la misma fuente,
- utilicen el mismo sistema,
- compartan los primeros steps.

Si posteriormente producen procesamiento adicional o un outcome
funcional diferente, deben generar cobertura independiente.

Las ejecuciones periódicas pueden agruparse únicamente cuando:

- mantengan el mismo flujo,
- tengan el mismo procesamiento funcional,
- y produzcan el mismo resultado.

Si una ejecución especial, cierre, corte o ejecución final incorpora
análisis, validaciones o resultados adicionales, debe evaluarse como
un escenario independiente.

=================================================
3.4) RN Y EXC
=================================================

RN:

- Si representa comportamiento exitoso, validarla dentro del
  Happy Path.
- Si provoca un resultado alterno, utilizar classification="exception".
- RN procesadas en el mismo momento y con la misma consecuencia
  pueden agruparse.

EXC:

- Cada EXC explícita con causa y comportamiento esperado debe
  recibir cobertura.
- action debe representar el trigger cuando sea necesario.
- expected debe representar la respuesta definida.
- No generar excepciones técnicas genéricas no descritas.

=================================================
3.5) PRUEBAS NO FUNCIONALES
=================================================

No generar TCs únicamente por:

- tiempo,
- rendimiento,
- volumen,
- capacidad,
- performance.

Si alguno de estos elementos produce una consecuencia funcional
explícita, puede evaluarse como exception.

=================================================
3.6) CANTIDAD DE STEPS Y TCs
=================================================

Máximo de steps:

- Cada TC debe tener máximo 10 steps.
- Consolidar acciones consecutivas relacionadas antes de dividir.
- Si todavía supera 10 steps, dividir por hitos funcionales.
- Cada TC resultante debe tener objective y expected_result propios.
- No utilizar nombres como "Parte 1" o "Parte 2".

Cantidad de TCs:

- No existe límite máximo fijo por requerimiento.
- Generar únicamente los TCs necesarios para cubrir sus comportamientos
  funcionales verificables.
- No reducir artificialmente cobertura.
- No aumentar artificialmente cantidad.
- Continuar aplicando Outcome + Trigger y reglas anti-redundancia.

=================================================
4) EVALUACIÓN DE CONCENTRACIÓN FUNCIONAL
=================================================

Generar además un requirement_review para evaluar la estructura
funcional del requerimiento completo.

Esta evaluación es independiente de la testeabilidad.

El análisis debe determinar si InputText representa:

- una capacidad funcional coherente,
- una capacidad con complejidad interna significativa,
- o varias capacidades funcionales independientes.

La clasificación NO debe basarse principalmente en:

- longitud del texto,
- cantidad de TCs,
- cantidad de steps,
- cantidad de PP,
- cantidad de RN,
- cantidad de EXC,
- sistemas,
- archivos,
- fuentes,
- bancos,
- actores,
- integraciones,
- transformaciones.

Estos elementos pueden existir en un requerimiento adecuado cuando
todos contribuyen al mismo resultado funcional.

Analizar principalmente:

- objetivo funcional principal,
- resultado de negocio,
- relación entre subprocesos,
- dependencia secuencial,
- outcomes diferentes,
- reglas pertenecientes a comportamientos diferentes,
- rutas funcionales independientes,
- capacidades que tengan propósito y resultado propios.

=================================================
4.1) ADEQUATE
=================================================

Utilizar "adequate" cuando el requerimiento represente una unidad
funcional cohesiva.

Debe cumplirse principalmente que:

- Existe un objetivo funcional principal.
- Existe un flujo funcional claramente relacionado.
- Los pasos, reglas, validaciones y excepciones forman parte de ese
  mismo comportamiento.
- Los posibles subprocesos son etapas dependientes del mismo flujo y
  no representan bloques que puedan probarse razonablemente de forma
  independiente.
- Las diferencias de sistemas, archivos, fuentes, actores,
  transformaciones o datos son únicamente parte de la ejecución del
  mismo comportamiento funcional.

Un requerimiento puede contener varios pasos, reglas, archivos,
sistemas o excepciones y continuar siendo "adequate".

Sin embargo, NO utilizar "adequate" cuando dentro del requerimiento
existan varios bloques funcionales claramente diferenciables que
posean procesamiento y resultado verificable propios, aunque todos
contribuyan a un objetivo superior común.

posean procesamiento y resultado verificable propios, aunque todos
contribuyan a un objetivo superior común.

=================================================
4.2) HIGH_CONCENTRATION
=================================================

Utilizar "high_concentration" cuando el requerimiento continúe
representando una sola unidad funcional principal, pero presente
complejidad interna significativa.

Puede existir:

- gran cantidad de reglas de negocio,
- múltiples decisiones,
- excepciones,
- variantes funcionales,
- diferentes rutas de ejecución,
- múltiples condiciones que cambien el procesamiento.

La diferencia frente a "saturated" es que estas variantes continúan
perteneciendo esencialmente al mismo comportamiento funcional y no
forman varios bloques funcionales suficientemente independientes.

Utilizar "high_concentration" cuando:

- existe un objetivo principal común,
- las rutas dependen del mismo proceso,
- las diferencias modifican cómo se alcanza el resultado,
- pero no existen múltiples bloques con procesamiento y validación
  propios suficientemente diferenciados.

NO utilizar "high_concentration" cuando el requerimiento contenga
varios bloques funcionales que puedan probarse razonablemente de
forma independiente.

=================================================
4.3) SATURATED
=================================================

Utilizar "saturated" cuando un mismo requerimiento agrupe múltiples
bloques funcionales claramente diferenciables.

NO es necesario que cada bloque represente un objetivo de negocio
completamente independiente.

Un requerimiento puede tener un objetivo superior común y aun así
estar saturated cuando dicho objetivo se encuentre compuesto por
varios subprocesos funcionales con comportamiento propio.

Considerar un bloque funcional independiente cuando presente varias
de las siguientes características:

- Tiene una finalidad funcional identificable dentro del requerimiento.
- Consume una fuente, input o artefacto específico.
- Aplica reglas de negocio o transformaciones propias.
- Ejecuta un procesamiento funcional diferenciable.
- Produce un resultado o estado verificable propio.
- Puede generar casos de prueba específicos sin depender de validar
  simultáneamente los demás bloques.
- Puede ser explicado y probado como una unidad funcional claramente
  distinguible.

Clasificar como "saturated" cuando existan múltiples bloques de este
tipo dentro del mismo requerimiento, aunque posteriormente sus
resultados se integren para alcanzar un objetivo superior común.

Ejemplo conceptual:

Un requerimiento cuyo objetivo general sea construir una base puede
estar saturated si dentro de él se definen de forma diferenciada:

- obtención de información desde una fuente A,
- obtención desde una fuente B,
- transformación de otra fuente,
- enriquecimiento de información,
- procesamiento de anexos,
- conciliación o actualización posterior,

si cada bloque posee reglas y comportamiento verificable propio.

NO clasificar como saturated únicamente porque existan muchos pasos,
archivos, sistemas, reglas o PP.

Debe existir diferenciación funcional real entre los bloques.

=================================================
4.4) REGLA DE DECISIÓN
=================================================

Seleccionar el nivel que represente mejor la estructura funcional
observada en InputText.

No reducir ni aumentar el nivel por precaución.

Orden de evaluación:

1. Identificar el objetivo funcional general.
2. Identificar los bloques funcionales internos.
3. Determinar si dichos bloques son únicamente pasos dependientes o
   si poseen comportamiento verificable propio.
4. Evaluar reglas, variantes y excepciones dentro de cada bloque.

Clasificar:

- "adequate":
  una unidad funcional cohesiva.

- "high_concentration":
  una unidad funcional cohesiva con complejidad interna significativa.

- "saturated":
  múltiples bloques funcionales diferenciables que pueden probarse
  razonablemente como unidades distintas, aunque contribuyan a un
  mismo objetivo superior.

Si existe evidencia clara de múltiples bloques funcionales
independientemente testeables, "saturated" tiene prioridad sobre
"high_concentration".

4.5) REQUIREMENT_REVIEW
=================================================

Generar siempre:

"requirement_review": {
  "level": "...",
  "reason": "...",
  "areas": [],
  "functional_blocks": []
}

level:

Debe contener únicamente:

- "adequate"
- "high_concentration"
- "saturated"

reason:

- Explicación breve y concreta.
- Indicar por qué se asignó el nivel.
- Basarse únicamente en InputText.
- Explicar la relación entre los comportamientos y el objetivo
  funcional principal.

areas:

- Lista de aspectos donde exista concentración funcional real.
- No incluir elementos únicamente porque aparezcan en el documento.

Ejemplos válidos únicamente cuando correspondan:

- "Reglas de negocio"
- "Excepciones"
- "Rutas funcionales"
- "Subprocesos funcionales"
- "Integraciones"
- "Transformaciones de datos"
- "Variantes funcionales"

Para adequate:
- Normalmente [].

Para high_concentration:
- Debe identificar dónde se concentra la complejidad.

Para saturated:
- Debe identificar dónde se encuentran las capacidades independientes.

functional_blocks:

- Debe contener responsabilidades o capacidades funcionales,
  no simples pasos.
- No incluir PP, sistemas, archivos, fuentes o actividades
  secuenciales como bloques independientes.

Para adequate:
- Normalmente [].

Para high_concentration:
- Normalmente [].
- Puede contener bloques diferenciables cuando todavía dependan
  del mismo objetivo funcional.

Para saturated:
- Debe contener las principales capacidades funcionales
  independientes que justifican la clasificación.
- Deben provenir directamente de InputText.
- No inventar nombres.

=================================================
5) REDACCIÓN DE CADA CAMPO DEL CASO DE PRUEBA
=================================================

Esta sección es obligatoria y debe aplicarse exactamente a todos
los casos generados.

-------------------------------------------------
5.1) classification
-------------------------------------------------

Debe contener únicamente:

- "happy_path"
- "exception"

No utilizar ningún otro valor.

-------------------------------------------------
5.2) objective
-------------------------------------------------

- Debe ser exactamente 1 oración.
- Máximo 240 caracteres.
- Debe iniciar obligatoriamente con:

  "Que el bot"

- Debe expresar el comportamiento funcional a validar.
- Debe indicar QUÉ se valida, no describir todos los pasos.
- Debe ser claro, directo y verificable.
- No debe incluir más de un objetivo principal.
- No debe incluir información ausente en InputText.

Ejemplo:

"Que el bot procese el reporte detallado aplicando las reglas de
negocio y genere el archivo de salida correspondiente."

-------------------------------------------------
5.3) expected_result
-------------------------------------------------

- Debe ser un solo párrafo.
- Máximo 2 oraciones cortas.
- Debe representar el resultado final del TC.
- No debe enumerar todos los pasos.
- Debe ser verificable.

Para happy_path:

- Describir las acciones funcionales principales y el resultado
  exitoso final.

Para exception:

- Describir la condición detectada y la respuesta funcional
  esperada definida en InputText.

-------------------------------------------------
5.4) preconditions
-------------------------------------------------

preconditions debe ser SIEMPRE una lista JSON.

Cada elemento debe representar una precondición independiente.

Puede incluir únicamente información explícita o referenciada:

- accesos,
- sistemas,
- insumos,
- actor,
- configuraciones,
- estados previos,
- archivos necesarios.

Reglas:

- No inventar precondiciones.
- No utilizar una precondición como step.
- Si no existen precondiciones aplicables, devolver [].

Ejemplo:

"preconditions": [
  "Contar con el archivo de entrada definido",
  "Tener acceso al sistema indicado"
]

-------------------------------------------------
5.5) steps
-------------------------------------------------

steps debe ser una lista JSON.

Cada elemento debe contener exactamente:

- action
- expected

Cada step debe representar una acción funcional observable y
verificable.

Máximo 10 steps por TC.

-------------------------------------------------
5.6) action
-------------------------------------------------

Cada action debe iniciar obligatoriamente con:

"Validar que el bot"

Después de esa frase:

- utilizar un verbo que represente claramente la acción,
- describir una acción observable,
- mantener el orden funcional del requerimiento,
- conservar nombres técnicos exactamente cuando corresponda,
- mencionar RN o EXC cuando ayude a la trazabilidad.

No utilizar acciones genéricas.

No agregar acciones no descritas.

Si varias variantes pertenecen al mismo outcome, pueden integrarse
en el mismo step cuando sea claro.

Ejemplos:

"Validar que el bot ingrese las credenciales correspondientes en
Turnex."

"Validar que el bot seleccione la empresa correspondiente."

"Validar que el bot descargue el reporte de Trabajadores No
Controlados."

"Validar que el bot registre la marca faltante del trabajador."

-------------------------------------------------
5.7) expected
-------------------------------------------------

- Debe representar el resultado esperado observable del step.
- Cuando exista Criterio de Aceptación asociado, utilizarlo como base.
- No repetir simplemente la action.
- No inventar validaciones.
- Debe ser breve y verificable.
- Si no existe criterio explícito, redactar únicamente el resultado
  directamente derivable de la acción y comportamiento descritos.

=================================================
6) REQUERIMIENTO NO TESTEABLE
=================================================

Si InputText no permite comprobar ningún comportamiento funcional:

- No inventar TCs.
- No inventar resultados.
- No generar steps.
- Explicar concretamente qué información falta.
- Indicar qué debe definirse para permitir pruebas posteriormente.
- Generar requirement_review de todas formas.

La testeabilidad y la concentración funcional son evaluaciones
independientes.

La salida debe ser:

{
  "test_cases": [],
  "not_testable": {
    "objective": "...",
    "reason": "...",
    "missing_information": "...",
    "required_definition": "..."
  },
  "requirement_review": {
    "level": "adequate",
    "reason": "...",
    "areas": [],
    "functional_blocks": []
  }
}

El level anterior es únicamente ilustrativo.

-------------------------------------------------
6.1) objective DE not_testable
-------------------------------------------------

- Exactamente 1 oración.
- Debe iniciar con "Que el bot".
- Describir el comportamiento que se pretendía validar.
- No inventar información.

-------------------------------------------------
6.2) reason
-------------------------------------------------

- Explicar concretamente por qué no puede probarse.
- No usar frases genéricas como "falta información".
- Indicar qué impide determinar comportamiento verificable.

-------------------------------------------------
6.3) missing_information
-------------------------------------------------

Indicar específicamente qué falta:

- dato,
- regla,
- criterio,
- condición,
- resultado esperado,
- comportamiento.

-------------------------------------------------
6.4) required_definition
-------------------------------------------------

Indicar qué debe definir o aclarar el documento para permitir
posteriormente la generación de TCs.

=================================================
7) TRAZABILIDAD FUNCIONAL
=================================================

Cuando un TC cubra una RN o EXC:

- mencionar su identificador dentro de action, expected o
  expected_result cuando aporte claridad.
- no saturar la redacción con identificadores innecesarios.

Ejemplos:
